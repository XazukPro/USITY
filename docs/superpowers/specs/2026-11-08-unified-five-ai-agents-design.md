# USITY: единая связка пяти AI-агентов

## Цель

Превратить разрозненные прототипы в один серверный контур MVP. Один доверенный
worker получает сообщения **только подключенной Telegram-темы**, собирает
`EventBundle` и независимо запускает пять явно именованных агентов. Каждый
результат остаётся черновиком. Только действие администратора может создать,
изменить, отменить ДЗ или опубликовать материал.

## Выбранный подход

1. **Выбран — общий контракт и единый оркестратор FastAPI.** Полезные правила
   прототипов переносим в `backend/app/agents/`; агентам доступен только
   read-only срез bundle. Оркестратор сохраняет все предложения одной карточкой
   проверки. Это делает пять агентов видимыми, тестируемыми по отдельности и
   пригодными для одной очереди админа.
2. Почти дословно слить feature-ветки быстрее, но оставит несовместимые
   структуры входов, разные провайдеры и невозможность одной очереди.
3. Оставить их отдельными демо-модулями не создаст рабочий MVP-поток.

## Пять агентов

| ID | Роль | Самостоятельный результат |
| --- | --- | --- |
| `homework_detection` | Обнаружение нового ДЗ | Текст нового ДЗ и ID сообщений-источников. |
| `schedule_binding` | Привязка к расписанию | Предмет, подгруппы, будущая пара и флаги неоднозначности. |
| `duplicate_conflict` | Дубли и противоречия | Похожие активные ДЗ, объяснение и кандидаты для решения админа. |
| `material_proposal` | Учебные материалы | Файл/ссылка, предметы, категория и связь с ДЗ; фото использует уже извлечённый OCR. |
| `assignment_change` | Изменения и отмены | Целевое опубликованное ДЗ, тип изменения и предлагаемые новые значения. |

Каждый агент имеет отдельный модуль, prompt-version, строгую проверку ответа,
точку вызова и unit-тесты. Пять вызовов не используют результаты друг друга.

## Контракт и поток

`EventBundle` содержит идентификаторы группы/чата/темы, соседние сообщения,
вложения и OCR raw/corrected, опубликованное расписание, предметы,
подгруппы, активные ДЗ, материалы и категории. Личные задачи и материалы
исключены. До вызова LLM worker проверяет соответствие подключенному источнику
и ограничивает размер пакета.

Агенты возвращают единообразный `AgentProposal`: `agent_id`, `proposal_type`,
ID источников, поля предложения, обоснование, флаги неопределённости, версии
модели и промпта. Некорректный ответ агента становится ошибкой worker, а не
ложным «ничего не найдено». Ответ каждого агента сохраняется отдельно от
последующего решения человека.

Оркестратор всегда запускает все пять агентов на одном bundle и сохраняет одну
карточку очереди. В карточке API явно возвращает все пять слотов (включая
`not_found`), исходный контекст и расхождения. Админ может принять, поправить,
объединить или отклонить предложение. Первая конкурирующая запись решения
побеждает; остальные получают актуальный статус.

## Публикация

Публикация нового ДЗ сохраняет привязку к паре. Решение по материалу создаёт
групповой материал только после проверки админа. Решение об изменении или
отмене находит существующее ДЗ по версии и обновляет либо скрывает его лишь
после действия администратора. Дубли — сигнал для карточки и никогда не
выполняют автоматическое объединение/удаление. Существующий endpoint одобрения
ДЗ остаётся совместимым на переходный период.

## Границы

- Telegram-бот, реальный OCR-провайдер, очередь Redis и миграции production-БД
  не создаются этой задачей. OCR передаётся в bundle через заменяемый адаптер;
  документы не читаются.
- Реальные ключи, чаты и результаты LLM не добавляются в Git. Тесты используют
  синтетические данные и фиксированные ответы провайдеров.
- До отдельного размеченного набора тесты доказывают корректность контрактов и
  защитных правил, но не заявляют точность модели.

## Проверка

Для каждого агента — отдельные unit-тесты формата, изоляции от чужой темы,
источников и неопределённости. Сквозной integration-тест докажет, что один
bundle даёт пять явно маркированных результатов, создаёт только черновик, а
одобрение/отклонение выполняется человеком.
