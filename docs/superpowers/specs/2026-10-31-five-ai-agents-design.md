# USITY: пять независимых AI-агентов — проектное решение

Дата: 31.10.2026. Статус: проектный план; код агентов пока не создается.

## Зачем это нужно

Учебное требование: пять участников команды разрабатывают минимум по одному AI-агенту. При этом USITY сохраняет исходную цель MVP: из выбранной Telegram-темы получать предложения по ДЗ и материалам, показывать их администратору и публиковать только после его решения. Финальная сдача — 15.12.2026.

## Подходы

1. **Выбран: пять независимых специализированных агентов.** Каждый вызывается отдельно на общем подготовленном контексте, имеет свою задачу, правила, инструменты и оценку качества. Сервер сопоставляет предложения и передает их администратору. Это дает каждому участнику самостоятельную работу и не раздувает продуктовый MVP.
2. Последовательная цепочка из пяти шагов проще для первого прототипа, но ошибка раннего шага блокирует остальные, а отдельные части трудно демонстрировать независимо.
3. Пять полных систем «сообщение → готовое ДЗ» означали бы дублирование логики, затрат и ответственности. Для срока MVP это неоправданно.

Независимость означает, что агента можно запустить и оценить отдельно; ему не нужен ответ другого агента для выполнения своей задачи. Общие инфраструктура, LLM-провайдер и схема данных допустимы. Пять разных промптов к одной модели сами по себе не считаются пятью агентами: у каждого должен быть собственный сценарий принятия решения, ограниченный набор доступных инструментов, структурированный результат и набор проверочных примеров.

## Общий контракт

Backend формирует **EventBundle** из выбранной Telegram-темы: ID и время сообщений, текст, ссылки на вложения, OCR фото, текущие предметы, расписание и опубликованные ДЗ группы. Сбор соседних сообщений и фильтрация по теме выполняются общим слоем до запуска агентов. Личные задачи и личные материалы в этот контекст не входят.

Каждый агент получает нужную ему часть EventBundle и доступ только к чтению необходимых данных. Результат — **AgentProposal**: идентификатор агента, тип предложения, ID исходных сообщений, предлагаемые поля, обоснование, признаки неопределенности, версии модели и промпта. Агент может вернуть «не найдено». Предложения объединяются по исходным сообщениям; расхождения сохраняются для админа, а не разрешаются автоматически.

Все пять агентов вызываются независимо. Например, агент сроков может прочитать исходный текст и расписание без результата агента ДЗ; агент дублей — исходный текст и список действующих заданий. Один и тот же EventBundle можно прогнать через каждого агента по отдельности на демонстрации.

В очереди админа одно событие представлено одной карточкой. В ней видны исходные сообщения, предложения с указанием агента и итоговые поля для правки. Если агенты расходятся, карточка показывает расхождение и требует выбора админа. Его итоговое решение записывается отдельно от всех исходных предложений.

## Границы и безопасность

- Агентам запрещены публикация, изменение или удаление групповых данных. Любое действие с ДЗ и групповым материалом подтверждает админ в приложении.
- Telegram-сообщения и OCR считаются недоверенным вводом: текст чата не может менять инструкции, инструменты и границы доступа агента.
- Обрабатывается только подключенная тема; документы не читаются изнутри, фото проходят OCR. Неподдерживаемые файлы отсекаются до агентов.
- Для будущего дообучения сохраняются входной контекст кандидата, OCR raw/corrected, ответы агентов, правки и решения админа, версии модели и промпта. Доступ к данным ограничивается; реальные чаты не попадают в Git.
- Сомнительное предложение остается черновиком для админа. Отсутствие уверенности не превращается в автоматическую публикацию.

## Как доказать независимость и качество

Для каждого агента нужны отдельная точка вызова, набор размеченных примеров, проверка формата ответа и демонстрация без запуска остальных агентов. Начальный набор можно собрать из обезличенных или специально созданных учебных сообщений; реальные сообщения вносятся только при наличии необходимых согласий. Общая сквозная демонстрация: сообщение в Telegram → предложения нескольких агентов → очередь проверки → действие админа → ДЗ или материал в приложении.

Отдельно измеряем: обнаружение реальных ДЗ, правильность привязки к предмету и паре, точность категоризации материалов, обнаружение изменений/отмен, полезность сигналов о дублях. Общие метрики USITY сохраняются: время до черновика и корректная публикация после подтверждения. Целевые пороги установим после разметки контрольного набора; до нее не будем объявлять произвольные проценты качества.

## Что остается уточнить перед реализацией

- Формальный критерий преподавателя для «независимого агента» и требования к индивидуальной демонстрации.
- Фактический объем и источник обезличенного набора примеров для каждого агента; до их получения метрики остаются планом измерения.
- Для LLM выбран GigaChat API в доступном бесплатном режиме; перед интеграцией проверяем лимиты и качество модели. OCR-провайдер и формат общей интеграции еще требуют уточнения; провайдеры остаются заменяемыми адаптерами.

Реализация, установка новых зависимостей и создание исходного кода начинаются только после отдельного решения команды.
