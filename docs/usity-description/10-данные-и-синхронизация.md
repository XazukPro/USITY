# Данные, сроки хранения и синхронизация

## Логическая модель

| Данные | Привязка и назначение |
| --- | --- |
| Аккаунт, email, сессии | Авторизация и восстановление доступа |
| Учебная группа, членство и роль | Изоляция пользователей и полномочий |
| Приглашение | Присоединение к конкретной группе |
| Семестр, предметы, подгруппы | Общий каталог и учебные периоды |
| Выбор подгруппы | Персональная видимость по каждому предмету |
| Расписание и исключения | Повторяющиеся и разовые пары, привязка к конкретной дате |
| Групповое ДЗ и версия | Подтверждённый текст, занятие, видимость и изменения |
| Выполнение ДЗ | Личное состояние участника и версия задания |
| Личная задача | Текст, дата, время, продолжительность и выполнение |
| Материал | Файл или ссылка, видимость, категория и связи с предметами и заданиями |
| Подключение Telegram и сообщения | Проверенный источник и контекст события |
| Предложение агента и решение | Источники, вывод, исправления, версии и результат проверки |
| Настройки и push-токены | Предпочтения и доставка уведомлений |

Названия выше описывают предметную область. Схема текущей базы и миграции находятся в [backend/migrations](../../backend/migrations).

## Поток сохранения

Клиент обращается к API через HTTPS в целевом окружении. Сервер проверяет сессию, группу, роль и подгруппу. Текст и метаданные хранятся в PostgreSQL, файлы — в закрытом S3-совместимом хранилище. Локальный стенд использует SQLite и приватный каталог. На устройстве SQLite хранит доступные данные и незавершённые изменения, а сессия помещается в защищённое хранилище.

Входящее событие получает устойчивый идентификатор. Исходные сообщения и контекст фиксируются для проверки и повторной обработки. По каждому агенту сохраняются результат или ошибка, версия модели и промпта. Решение администратора и публикация должны выполняться согласованно, чтобы повторный запрос не создавал второй записи.

## Синхронизация и конфликты

1. После первого получения клиент может показать сохранённое расписание и материалы без сети.
2. Изменение личной задачи или отметка ДЗ записывается на устройство и ожидает синхронизации.
3. После появления сети запрос повторяется с идентификатором операции и версией.
4. При разных правках личной задачи пользователь сравнивает свою и серверную версии и выбирает нужную. После истечения архива локальную копию можно сохранить как новую задачу.
5. Если админ выпустил новую версию ДЗ, устаревшая отметка не скрывает новую версию.

Административная публикация и проверка требуют сети. Ранее скачанные файлы доступны на устройстве. Членство, роль и видимость проверяются сервером при подключении.

## Сроки

| Данные или событие | Согласованное правило |
| --- | --- |
| Выполненная личная задача | Доступна в списке для восстановления три дня |
| Группа после удаления owner | Восстановление в течение семи дней с возвращением участников |
| ДЗ после окончания семестра | Скрывается, техническое хранение 30 дней, затем удаление или обезличивание |
| Материалы предмета | Сохраняются в архиве и между семестрами |
| Личные данные удалённого аккаунта | Удаляются по утверждённому сценарию |
| Групповые записи после удаления участника | Сохраняются с обезличиванием |

Физическая очистка, резервные копии и точные сроки исходных Telegram-сообщений и датасета требуют отдельной реализации и утверждения до пилота.

## Оценка и обучение AI

Для анализа качества предполагается хранить входной контекст, сырой и исправленный OCR, предложение, правки и решение администратора, версию модели и промпта. Доступ к этим данным ограничивается ролью и целью обработки. Обучающий набор готовится отдельно с проверкой разрешений и обезличиванием. Факт накопления данных не означает готовность или качество дообученной модели.
