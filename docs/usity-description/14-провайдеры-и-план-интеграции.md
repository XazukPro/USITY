# Провайдеры и план интеграции USITY

Дата исследования — 10 ноября 2026 года. Документ фиксирует предлагаемые технические решения. Создание платных ресурсов, бюджет, договоры, доступы и обработка реальных сообщений требуют отдельной настройки. Текущая степень готовности указана в [статусе](08-статус-и-метрики.md).

## Предлагаемый набор

| Задача | Основной вариант | Дальнейшая проверка |
| --- | --- | --- |
| Текстовая модель | GigaChat API, `GigaChat-2` для первого измерения | Доступность модели в аккаунте, качество на размеченной выборке, цена и задержка. `GigaChat-2-Pro` — кандидат для сравнения сложных случаев |
| Фото | Yandex Vision OCR через заменяемый адаптер | Качество русского печатного и рукописного текста на добровольной обезличенной выборке, цена и сроки хранения. Сравнить с доступной мультимодальной моделью GigaChat |
| API и процессы | Yandex Cloud Compute VM, Docker Compose для пилотного стенда | Квоты, стоимость, восстановление и условия размещения. API, Telegram-приёмник и worker запускаются отдельными процессами |
| Структурированные данные | Yandex Managed Service for PostgreSQL | Смета и доступность; локально PostgreSQL и SQLite. Миграции, резервное копирование и восстановление проверяются заранее |
| Файлы | Yandex Object Storage, приватный S3-бакет | Проверить реальную совместимость существующего boto3-адаптера, лимиты, резервное копирование и стоимость операций |
| Очередь | Redis в Yandex Cloud, фоновый Python-worker | Фиксировать источник истины в PostgreSQL, выбрать конкретный механизм очереди после проверки надёжной повторной доставки |
| Email-коды | Yandex Cloud Postbox по SMTP | Домен отправителя, проверка TLS, доставка на популярные российские почтовые сервисы и лимиты |
| Push iOS | APNs | Учётная запись Apple Developer, подпись, сертификаты/ключ и проверка на физическом iPhone |
| Push Android | RuStore Push для сборки RuStore, адаптеры дополнительных каналов | Доступность сервиса доставки у студентов, тесты на физических устройствах и выбор дополнительного канала |
| Разработка и релиз | Flutter, FastAPI, aiogram, SQLAlchemy, GitHub Actions; Android Studio, Xcode и симуляторы | Настроить CI, локальный запуск и сборки на конкретных версиях зависимостей |

Выбор Yandex Cloud предложен для единого размещения инфраструктуры. GigaChat остаётся отдельным провайдером модели. Резервная конфигурация — возможность заменить OCR, LLM, SMTP и S3 через интерфейсы. Тариф и объём затрат до измерений не заявляются.

Источники: [модели GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/selecting-a-model), [авторизация GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api), [тарифы GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/tariffs), [Yandex Vision OCR](https://yandex.cloud/ru/services/vision-ocr), [Yandex Object Storage](https://yandex.cloud/ru/services/storage), [Yandex Cloud Postbox](https://yandex.cloud/ru/services/postbox), [RuStore Push](https://www.rustore.ru/help/sdk/push-notifications).

## Где работает каждый компонент

1. Телефон запускает Flutter, хранит данные offline в SQLite и обращается по HTTPS к FastAPI. Токены модели и Telegram на телефон не передаются.
2. Приёмник Telegram получает сообщение, проверяет группу и тему, фиксирует идентификатор, время, текст и допустимые метаданные в PostgreSQL. Медиаконтент скачивается только для разрешённой темы, файл сохраняется приватно.
3. Worker получает событие из очереди, объединяет связанные сообщения и фото, запускает OCR и формирует неизменяемый пакет с источниками и групповым контекстом. Прежде чем сохранять результат после вызовов, ещё раз проверяется подключение.
4. Пять независимых модулей получают разрешённый пакет. Модель GigaChat возвращает результат каждого агента; сервер проверяет формат и ссылки на источники. Ошибка агента фиксируется как ошибка, сохраняются результаты остальных.
5. Староста редактирует и подтверждает каждое нужное действие в приложении. Транзакция проверяет роль, группу, версию черновика, пару и подгруппы. Публикация порождает запись для отправки push. Админские изменения имеют приоритет при offline-синхронизации.
6. Для качества собираются входные данные, исходный OCR, исправление OCR, вывод модели, решение и правки администратора с версиями. Состав данных, доступ и возможность будущего обучения согласовываются до работы с настоящими чатами.

## Особенность текущего GigaChat-адаптера

В `backend/app/agents/providers.py` есть OAuth, кеш токена, проверка TLS и обработка ошибок GigaChat. Для каждого экземпляра адаптера можно передать собственную JSON-схему, прежняя схема поиска ДЗ остаётся схемой по умолчанию. У остальных четырёх агентов другие форматы ответа. При интеграции необходимо определить и подключить соответствующую схему для каждого агента и проверять её локально. Ошибка модели должна оставаться ошибкой. Ветка пяти агентов использует общий интерфейс `complete(system_prompt, event_json)`; совместимость контракта надо обеспечить адаптером.

На первом этапе разрешена проверка на синтетических данных и тестовых ответах. Для реального запроса потребуются проект GigaChat API, тип доступа и секрет, а также проверка доверенной цепочки сертификатов. По документации новый целевой адрес API — `https://api.giga.chat`. Секреты не передаются в чат и не помещаются в Git.

## Дообучение и качество

GigaChat API рассматривается как базовая модель для первого прототипа. Возможность, условия и способ дообучения конкретной модели GigaChat в выбранном тарифе не подтверждены: проверить с провайдером до выбора процедуры. Параллельно подготовить набор допустимых обезличенных примеров и независимый тестовый набор по целым эпизодам переписки. Сравнивать найденные и пропущенные ДЗ, правильность предмета, пары, срока, подгруппы, а также ложные предложения. Промпты и версии фиксируются. По согласованному MVP админ проверяет результат.

## Очередность и критерии

1. **Совместимость GigaChat и агентов.** В отдельной ветке объединить код с сохранением мобильной реализации. Протестировать пять разных схем, исходные ссылки и независимое сообщение об ошибке. Проходят прежние тесты обоих контуров.
2. **Единый Telegram-поток.** Связать разрешённую тему и стабильный контекст с пятью агентами. Повторная доставка не создаёт дубля, соседняя тема не доходит до AI, отключение во время запроса не публикует результат.
3. **Проверка и публикация.** Экран показывает все предложения. Сервер отдельно применяет создание, правку, отмену и материал после решения админа. Проверить старые черновики и гонку двух админов.
4. **OCR и вложения.** Подключить заменяемый OCR, подписи, фото и файлы. Синтетические изображения и учебные файлы проходят путь до проверки, недопустимые форматы отклоняются.
5. **Локальная сквозная демонстрация.** На двух клиентах показать путь нескольких сообщений до личной видимости ДЗ у пары, включая offline и подгруппы. Измерить задержку, ошибки и число вызовов модели.
6. **Тестовая инфраструктура и пилот.** Рассчитать смету, выбрать и оформить аккаунты, настроить домен/HTTPS, секреты, базу, файлы, почту и бота. Проверить восстановление из копий и физические устройства. Затем подключать добровольную группу.
7. **Уведомления и выпуск.** Реализовать согласованные push и ручное ДЗ, подготовить TestFlight, RuStore, документы и сборки, провести приёмочные проверки до сдачи 15 декабря.

## Открытые условия для подключения

- Доступ к проекту GigaChat API и тариф. Учётные данные задаются локально или в секретах сервера.
- Планируемый ежемесячный бюджет на API и тестовый стенд, число пилотных групп и ожидаемый объём фотографий/сообщений.
- Владелец домена, аккаунтов облака, почты и мобильных магазинов.
- Условия обработки данных авторов сообщений и несовершеннолетних, договор с поставщиками и сроки удаления. Проверить отдельно с ответственным специалистом.
- Наличие физического iPhone и Android для проверки push и системных просмотрщиков.
