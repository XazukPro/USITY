# USITY: архитектура реализации

Статус: проектное решение v0.1 от 02.11.2026. Исходные требования: [MVP](../product/mvp.md) и [пять агентов](../superpowers/specs/2026-10-31-five-ai-agents-design.md). Реализация по небольшим PR; плановый работающий MVP — 15.12.2026.

## Ответственность команды

Антон и Codex ведут Flutter-приложение, общий backend, Telegram-интеграцию, хранилище, offline и интеграцию. Алексей, Владислав, Иван и Дмитрий ведут только своих AI-агентов; Антон — агент обнаружения ДЗ. Для агентов обязателен единый [контракт](agent-contract-v0.md). Любое изменение схемы согласуется в Issue #1 и отдельном PR до обновления потребителей.

## Форма системы

Один репозиторий, модульный backend и мобильный клиент. FastAPI обслуживает мобильное приложение; PostgreSQL — источник истины; S3-совместимое хранилище — содержимое файлов; Redis и worker — фоновые OCR/LLM/уведомления. aiogram принимает Telegram updates и передает события в backend. Flutter хранит опубликованный снимок и очередь допустимых действий в SQLite. OCR/LLM, email и push вызываются через адаптеры, чтобы провайдера можно было заменить без изменения доменных правил.

Поток: Telegram update → проверка подключенного `chat_id`+`message_thread_id` → идемпотентное сохранение источника → группировка соседних сообщений → OCR фото → EventBundle → пять независимых вызовов → проверка AgentRunResult → одна карточка ReviewEvent → действие админа → транзакционная публикация → синхронизация и push затронутым студентам. Ошибка одного агента не блокирует результаты остальных. Повтор Telegram update или фоновой задачи не создает дубль события/ДЗ.

## Границы модулей

| Модуль | Данные и правила |
| --- | --- |
| Identity/Groups | email-код, пользователь, membership, owner/admin/student, приглашение, одна группа на пользователя, передача прав и удаление |
| Academic | semester, subject, subgroup, выбор студента, schedule draft/published, занятия и разовые изменения |
| Assignments | групповое ДЗ привязано к конкретной паре; версия ДЗ; личный completion; личные задачи отдельно |
| Materials | metadata, категории, связи с несколькими предметами/ДЗ, файл в object storage, личная/групповая видимость |
| Ingestion/Agents | одна Telegram-тема; EventBundle; OCR; независимые AgentRunResult; версии промпта/модели |
| Review/Audit | черновики, конфликтующие предложения, решение человека, технический аудит; только этот модуль публикует групповые данные |
| Sync/Notifications | снимки для offline, очередь локальных действий, разрешение конфликтов, адресные push |

API и БД создаются по вертикальным срезам, не отдельным большим PR на все таблицы. Первое ядро: вручную созданная пара → учебный EventBundle → предложение Антона → проверка админом → ДЗ внутри пары. Затем подключаются Telegram и остальные агенты.

## Инварианты

- Никакой агент и Telegram-бот не записывает опубликованное ДЗ напрямую. Админское решение проверяет роль, версию черновика и делает публикацию атомарно.
- `Assignment` имеет ссылку на конкретный экземпляр занятия (дата и slot), поэтому дедлайн отображается под нужной парой. Изменение ДЗ повышает версию; обязательный сброс completion применяется к изменениям срока/объединению дубля.
- `AssignmentCompletion` принадлежит студенту. Админ не получает статистику выполнения других пользователей.
- Удаление/отмена и повторный запуск требуют идемпотентных ключей и аудита. Черновики и сообщения не видны студенту до публикации.
- Все запросы проверяют membership и group scope. Источник Telegram проверяется до OCR и LLM. Личные материалы/задачи не включаются в EventBundle.
- Файлы ограничены 100 МБ и допустимыми типами. Содержимое документа не читается AI; OCR применяется к фото.
- Offline запись разрешена только для completion и личных задач; при конфликте новая версия ДЗ админа побеждает старый completion.

## Последовательность реализации

1. Общий контракт и синтетические fixtures; автономный агент Антона и адаптер LLM.
2. API для группы, семестра, предмета, конкретного занятия, ручной публикации и списка ДЗ; Flutter экран дня на обоих симуляторах.
3. ReviewEvent и админское подтверждение; соединить с агентом Антона на учебном EventBundle.
4. Telegram тема, группировка, OCR, оставшиеся четыре агента и агрегатор.
5. Материалы, личные задачи, offline, push, удаление и семестровые правила; затем сквозные проверки и метрики.

Для КП2 до 05.11, 12:00 показываем только фактически работающие компоненты и явно указываем, какие соединены между собой. Для КП3 до 15.12, 12:00 требуется полный согласованный MVP. Этапы и сравнение плана с фактом ведутся в Issue #15.

## Решения, не блокирующие ядро

LLM-провайдер пока не выбран. Адаптер принимает URL, модель и ключ из локального окружения; до выбора провайдера тесты используют подменный ответ, а качество модели не заявляется. Для первоначального учебного стенда email может отправляться через локальный тестовый канал, но рабочая авторизация требует согласованного почтового провайдера. Реальные чаты и ключи в Git не помещаются.
