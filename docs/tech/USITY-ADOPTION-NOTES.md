# Сверка дизайн-handoff с существующим USITY

Статус: решения по пяти расхождениям приняты; реализация по обновлённому плану не начата. Дизайн-эталоны `docs/design/` сохранены из архива без правок. Продуктовые правила, архитектура и план адаптированы к действующему USITY. Оригинал корневых инструкций архива лежит в `HANDOFF-AGENTS.md`.

## Подтверждённый стек

Действующий выбор USITY: Flutter/Dart для iOS и Android; Python/FastAPI для API; aiogram для Telegram-бота; PostgreSQL для данных; S3-совместимое файловое хранилище; Redis с очередью задач для OCR/LLM; SQLite на устройстве для offline. В handoff предложены Expo/TypeScript, Supabase либо NestJS, grammY — это несовместимая стартовая рекомендация. Этапы `BUILD-PLAN.md` следует переносить на действующий стек, не создавая второй мобильный клиент и второй backend.

## Что можно использовать сразу

- `tokens.json`, эталонные PNG и HTML-прототипы задают внешний вид обоих режимов.
- Этапы 0–3 описывают последовательность построения UI, которую можно применить к Flutter после адаптации названий компонентов и тестовых инструментов.
- Ревью AI-черновика админом, привязка ДЗ к паре, личные задачи и пересечение во временной сетке совпадают с направлением проекта.

## Принятые решения

1. **Новое правило:** на оси дня у пары только `ДЗ · N`; пункты открываются внутри пары и видны в общем списке «Задачи». Выполненные пункты остаются зачёркнутыми и доступны для восстановления, без трёхдневного архива ДЗ.
2. **Старая логика:** один owner, несколько admin, student; owner управляет назначением админов и интеграцией.
3. **Старая логика:** подгруппы создаются по предметам, студент выбирает по одной для каждого предмета, ДЗ может адресоваться нескольким подгруппам.
4. **Старая логика:** пять AI-агентов, ручное ДЗ админа, материалы, базовый offline и ранее согласованные push входят в MVP. Виджеты и напоминания перед каждой парой не добавляются.
5. **Совмещение:** личная задача перемещается удержанием с шагом 5 минут и может пересекаться с парой. После выполнения она исчезает с оси, остаётся зачёркнутой в общем списке 3 дня с возможностью восстановления, затем скрывается.

## Порядок следующей работы

`BUILD-PLAN.md` адаптирован под Flutter/FastAPI и существующие компоненты. Реализовывать по одному этапу в отдельной ветке; проверять оба режима по `screens/*.png` и `prototype/*.html`. Этот документ не запускает следующий этап автоматически.
