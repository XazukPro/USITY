# Сверка дизайн-handoff с существующим USITY

Статус: документы импортированы; реализация по ним не начата. Архив сохранён без правок в `docs/design/`, `docs/product/PRODUCT-RULES.md`, `docs/tech/ARCHITECTURE.md` и `docs/tech/BUILD-PLAN.md`. Оригинал его корневых инструкций лежит в `HANDOFF-AGENTS.md`.

## Подтверждённый стек

Действующий выбор USITY: Flutter/Dart для iOS и Android; Python/FastAPI для API; aiogram для Telegram-бота; PostgreSQL для данных; S3-совместимое файловое хранилище; Redis с очередью задач для OCR/LLM; SQLite на устройстве для offline. В handoff предложены Expo/TypeScript, Supabase либо NestJS, grammY — это несовместимая стартовая рекомендация. Этапы `BUILD-PLAN.md` следует переносить на действующий стек, не создавая второй мобильный клиент и второй backend.

## Что можно использовать сразу

- `tokens.json`, эталонные PNG и HTML-прототипы задают внешний вид обоих режимов.
- Этапы 0–3 описывают последовательность построения UI, которую можно применить к Flutter после адаптации названий компонентов и тестовых инструментов.
- Ревью AI-черновика админом, привязка ДЗ к паре, личные задачи и пересечение во временной сетке совпадают с направлением проекта.

## Продуктовые расхождения для решения до соответствующих этапов

1. Старый MVP показывает невыполненное ДЗ внутри карточки пары в расписании и прячет выполненное на 3 дня в архив. Handoff показывает на оси только `ДЗ · N`, сами пункты — в открытой паре, а выполненное остаётся зачёркнутым в общем списке.
2. Старый MVP предусматривает owner, нескольких admin и student; handoff сводит управление к одной роли старосты и студента. Нужно сохранить управление правами владельца и админов.
3. Старый MVP разрешает подгруппы по предметам и видимость ДЗ для нескольких подгрупп; таблица `Subgroup` в handoff допускает общую подгруппу и единичный `subgroup_id` у ДЗ.
4. Старый MVP требует пять независимых AI-агентов, ручное добавление ДЗ админом, базовый offline, материалы и определённый набор push. Handoff описывает одного агента и предлагает виджет и напоминания перед парой, которых нет в утверждённом MVP.
5. Для личных задач был согласован перенос удержанием с шагом 5 минут и трёхдневный архив. Handoff уточняет вид и создание, но не описывает перенос жестом и оставляет выполненные задачи зачёркнутыми в общем списке.

## Порядок следующей работы

После выбора источника истины по пунктам выше: адаптировать `BUILD-PLAN.md` под Flutter/FastAPI и уже существующие компоненты; реализовывать по одному этапу в отдельной ветке; проверять оба режима по `screens/*.png` и `prototype/*.html`. До этого код не менять.
