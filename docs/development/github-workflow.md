# Работа команды в GitHub

Статус: организационный план на 31.10.2026. Разработка продукта еще не начата. Репозиторий: `XazukPro/USITY` (private). Цель MVP — 15.12.2026.

## Доступ

- Owner репозитория Антон приглашает по точным GitHub-логинам Алексея, Владислава, Ивана и Дмитрия: **Settings → Collaborators → Add people**. Проверить профиль перед отправкой приглашения; каждый принимает его в своем аккаунте.
- Репозиторий принадлежит личному аккаунту. В приватном репозитории приглашенный collaborator получает доступ на запись. Отдельную роль «только чтение» здесь назначить нельзя. Не передавать друг другу пароль, токены, SSH-ключи или доступ к облачным секретам.
- Всем участникам включить двухфакторную аутентификацию. Доступ к рабочему репозиторию выдавать только нужным людям; при выходе участника удалить его в **Settings → Collaborators** и отозвать выданные ему отдельные секреты, если они были.
- До приглашений проверить доступность защиты `main` в настройках тарифного плана. Для приватного репозитория GitHub Free на личном аккаунте правила защиты ветки могут быть недоступны; в таком случае командное правило «не отправлять напрямую в main» не является технической блокировкой. Варианты технического ограничения: тариф с защитой приватных веток или иной репозиторий/план, где эта функция доступна. Приватность не менять ради защиты ветки.

## Правила работы

1. **Одна задача = одна ветка = один PR.** Исходная ветка `main`; имена человеческих веток `feature/<issue>-<short-name>`, `agent/<issue>-<short-name>`, `docs/<issue>-<short-name>`. Для веток, которые создает Codex, префикс `codex/`.
2. Перед началом: `git switch main`, `git pull --ff-only`, `git switch -c agent/42-homework-detection` (номер и название заменить). Работу отправлять командой `git push -u origin <branch>`.
3. Коммитить маленькие логические изменения. В PR указать `Closes #<issue>`, что сделано, как проверено, что осталось. Черновой PR (`Draft`) допустим, чтобы показать промежуточную работу.
4. Перед объединением другой участник проверяет PR. Автор исправляет замечания. После проверок применять **Squash and merge**. Автор затем обновляет локальный `main` и создает новую ветку для следующей задачи.
5. Не делать `push` в `main` напрямую, `force push` в общие ветки, слияние без просмотра изменений. Не коммитить `.env`, токены, реальные чаты и персональные данные, локальные базы, сборки и SDK. В Git хранить только обезличенные или специально созданные примеры.
6. Если защита веток доступна: требовать PR и минимум одно одобрение другого участника, блокировать force push и удаление `main`, требовать разрешения обсуждений. Проверки CI сделать обязательными после появления рабочего CI; до этого требование несуществующей проверки заблокирует все PR. Владелец также следует процессу PR.
7. Конфликт с `main`: в своей ветке подтянуть актуальный `main`, разрешить конфликт, запустить относящиеся к изменению проверки и снова отправить ветку. При споре о контракте `EventBundle`/`AgentProposal` сначала согласовать изменение в Issue/PR, затем обновить потребителей.

## Рабочие блоки

GitHub Issues — перечень результатов, а не разрешение начинать код до решения команды. Каждый большой блок разбивать на PR, которые можно проверить за один обзор. Для каждого из пяти агентов нужен отдельный исполняемый компонент, вход/выход по общему контракту, автономный запуск, свои примеры и метрика качества. Подробнее: [проектное решение о пяти агентах](../superpowers/specs/2026-10-31-five-ai-agents-design.md).

| Блок | Основной ответственный | Результат |
| --- | --- | --- |
| Общий контракт и обезличенные примеры | Антон + вся команда | `EventBundle`, `AgentProposal`, правила версий и примеры для пяти агентов |
| Backend и данные | Антон (координация) | API групп, ролей, семестров, расписания, ДЗ, материалов и очереди проверки |
| Telegram-интеграция | Дмитрий | Подключение одной темы, сообщения и вложения, сбор соседних сообщений, безопасная передача событий |
| Агент обнаружения ДЗ | Антон | Предложение текста ДЗ и исходных сообщений |
| Агент привязки к расписанию | Алексей | Предложение предмета, подгрупп, пары и срока |
| Агент дублей и противоречий | Владислав | Сигнал о дубле/конфликте и оценочные примеры |
| Агент материалов | Иван | OCR фото, категория материала, связь с предметом/ДЗ |
| Агент изменений и отмен | Дмитрий | Предложение исправления/отмены существующего ДЗ |
| Очередь админа и публикация | Антон + Иван | Проверка, правка, решение человека, запись обратной связи; только админ публикует |
| Мобильное приложение | Иван (дизайн), команда (реализация) | Расписание, предметы/материалы, личные задачи, настройки, offline-чтение |
| Сквозная проверка и демонстрация | Владислав + вся команда | Сценарий Telegram → агенты → review → приложение, измеренные метрики |
