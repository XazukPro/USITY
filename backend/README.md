# Первый компонент: агент обнаружения ДЗ Антона

Это автономное ядро агента: принимает `EventBundle`, передает сообщения через интерфейс `LlmProvider`, проверяет JSON-ответ и выдает предложение `AgentProposal` или «не найдено». Сообщения могут содержать части одного ДЗ; предложение обязано ссылаться на существующие ID источников. Агент не публикует задание и не определяет предмет/пару.

Учебный запуск без зависимостей и ключей:

```bash
PYTHONPATH=backend python3 backend/demo_homework.py
PYTHONPATH=backend python3 -m unittest discover -s backend/tests -v
```

`demo_homework.py` использует заранее заданный ответ модели. Он проверяет маршрут данных и формат предложения, **не** доказывает качество LLM и **не** является интеграцией с Telegram. Следующий шаг: согласовать общий контракт в Issue #1, выбрать LLM-провайдера и измерить качество на размеченных примерах. Реальные чаты в Git не загружать.

Для настоящего вызова есть `ChatCompletionsProvider`: он принимает HTTPS endpoint сервиса с форматом Chat Completions, название модели и API-ключ. Настройте переменные окружения `USITY_LLM_ENDPOINT`, `USITY_LLM_MODEL`, `USITY_LLM_API_KEY` локально и запустите `PYTHONPATH=backend python3 backend/live_homework.py`. Скрипт отправляет только приведенные выше **синтетические** сообщения. Ключи не передавайте в чат и не коммитьте. Совместимость с конкретным провайдером и качество ответов пока не проверены; при выборе другого API будет отдельный адаптер.

## API проверки и публикации ДЗ

Первый серверный срез: конкретные пары, очередь проверки, одобрение/отклонение,
опубликованное ДЗ и личное выполнение. Поддерживаются PostgreSQL и локальная SQLite.
База хранит черновик, исходный контекст, сырой/разобранный ответ модели,
версии модели/промпта и итоговое решение с автором/временем. Публикация и решение
атомарны; конкурентные решения возвращают одному админу `409`.

Из корня репозитория (Python 3.14):

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.lock
.venv/bin/python -m pytest
.venv/bin/ruff check backend
PYTHONPATH=backend .venv/bin/python backend/demo_review.py
```

Демонстрация использует настоящие API-обработчики и временную файловую SQLite,
но **заранее заданный ответ модели**. Результат: до проверки — 0 ДЗ, после — 1;
после выполнения первым студентом — у него 0, у второго 1. Она не отправляет
сообщения в Telegram и не подтверждает качество реальной LLM.

### Локальный стенд с сохранением состояния

```bash
export USITY_DATABASE_URL='sqlite:///./usity-demo.sqlite3'
PYTHONPATH=backend .venv/bin/python backend/demo_review.py --prepare .env.demo-session
PYTHONPATH=backend .venv/bin/python -m uvicorn app.main:factory --factory --host 127.0.0.1 --port 8000
```

Открыть `http://127.0.0.1:8000/docs`. Файл `.env.demo-session` — JSON с ID группы,
пары, черновика и временными bearer-токенами админа и двух студентов. В Swagger
параметр `authorization` заполняется `Bearer <token>` из локального файла.
Срок сессий — 12 часов. Файл создается с правами `0600`, не перезаписывается
и игнорируется Git. Не отправляйте его в чат и не добавляйте в репозиторий.
Скрипт создает новую синтетическую группу при каждом запуске; не запускайте его
на рабочей базе. Завершив демонстрацию, удалите локальные demo-файлы.

Основные запросы:

| Метод и путь | Назначение |
| --- | --- |
| `GET/POST /groups/{group_id}/lessons` | Смотреть пары / создавать (admin/owner) |
| `GET /groups/{group_id}/review` | Очередь с источниками, только admin/owner |
| `POST /groups/{group_id}/review/{draft_id}/decision` | `action`, `expected_version`, для approve: `text` и `lesson_id` |
| `GET /groups/{group_id}/assignments` | Невыполненные ДЗ текущего пользователя |
| `PUT /groups/{group_id}/assignments/{id}/completion` | `version` и `completed`, только свой статус |

Роль и группа определяются по серверной сессии; клиент не может передать роль.
Токены в БД представлены SHA-256-хешами. Это временная подготовка доступа для
локального стенда, **не реализованная email-авторизация**.

### Проверка PostgreSQL

Только отдельная тестовая база (тесты создают синтетические записи):

```bash
docker run --name usity-review-test-db --rm -d \
  -e POSTGRES_PASSWORD=usity-local-test -e POSTGRES_DB=usity_test \
  -p 127.0.0.1:55432:5432 postgres:17-alpine
export USITY_TEST_DATABASE_URL='postgresql+psycopg://postgres:usity-local-test@127.0.0.1:55432/usity_test'
.venv/bin/python -m pytest
docker stop usity-review-test-db
```

Пароль выше предназначен исключительно для временной локальной тестовой БД.
Для запуска API на PostgreSQL задайте URL в `USITY_DATABASE_URL`. Создание схемы
пока выполняется явно учебным скриптом через `create_all`; API не меняет схему
при старте. Миграции Alembic потребуются до изменения существующей рабочей БД.

### Внутренняя интеграция агента

`app.ingestion.ingest_homework(engine, event_id, chat_id, bundle, provider,
model_version)` — доверенная функция worker, не публичный HTTP endpoint.
Проверяет подключенные chat/topic перед LLM и перед сохранением. Повтор того же
`group_id/event_id` возвращает прежний результат; другое содержимое с этим ID
вызывает конфликт. Конкурентные повторы могут вызвать LLM дважды, но создают
не более одного черновика. Ошибка модели отличается от «ДЗ не найдено» и может
быть повторена worker. Функция пока использует узкий контракт прототипа Антона;
общий контракт пяти агентов из PR #16 еще требует согласования.

### Границы этого этапа

Нет email OTP, приглашений, настройки Telegram через интерфейс, реального бота,
подгрупп, семестрового/повторяющегося расписания, файлов, push, синхронизации,
архива выполненных на 3 дня и административного изменения ДЗ. API пока не
подключен к Flutter. Создание пары означает создание одного конкретного занятия;
это не публикация полного расписания. Публичное размещение пока не предусмотрено.
Защита версий completion уже предусмотрена и проверена на изменении версии в БД;
полный offline-протокол будет отдельным этапом.

Текущий TestClient Starlette выдает предупреждение о будущем переходе с httpx
на httpx2. Оно не отключено; тесты пока используют зафиксированный совместимый
httpx 0.28.1. Это предупреждение зависимости, не результат качества LLM.

SQLite-стенд сериализует транзакции через `BEGIN IMMEDIATE`, поскольку SQLite
не поддерживает `SELECT FOR UPDATE`. Это сохраняет атомарность проверки версии
и источника, но ограничивает параллелизм локального стенда. PostgreSQL использует
блокировки строк. Ответ `409` при повторном решении содержит актуальные
`current_status`, `current_version`, `assignment_id`; клиент может показать
победившее решение без доступа к чужой группе.
